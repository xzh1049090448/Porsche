# A05 管理用户显示名编辑设计

日期：2026-09-08

## 1. 目标与范围

本切片关闭 PRD-260903 的 A05：管理者可修改其有权管理目标的显示名，同时伪造 `role`、`guid`、`auth_version` 或其他未声明字段的请求在任何持久化写入前被拒绝。

本切片只实现显示名编辑。用户名、角色、状态、密码、分组、套餐、允许模型、调用额度、权限覆盖、金额和删除均不进入通用 PATCH；它们继续由 A06–A11 的专属动作或 Mock 边界负责。旧 `PUT /admin/users/:guid` 不作为新界面的写入口，也不因本切片扩展能力。

## 2. 接口契约

新增并冻结：

- 方法与路径：`PATCH /admin/v2/users/{guid}`
- 能力：`users.edit`
- 请求头：现有 Bearer 认证；`Content-Type: application/json`
- 请求体上限：4 KiB，只接受一个 JSON object，不接受重复键、大小写折叠键、非法 UTF-8、尾随 JSON 或未知字段
- 请求字段：
  - `nickname`：必需；JSON `null` 表示清除显示名，字符串会去除首尾空白，结果必须为 1–64 个 Unicode code point
  - `expected_auth_version`：必需；1–2147483647 的 JSON 整数
- 明确禁止：`guid`、`username`、`role`、`auth_version`、`status`、`password`、`group_guid`、`plan_type`、`allowed_models`、`daily_call_limit`、`permission_overrides`、金额字段以及所有其他字段
- 成功：HTTP 200，返回现有 `UserReadDTO` 精确字段，带 `Cache-Control: no-store` 和非空 `X-Request-ID`
- 错误：400 非法路径/JSON/字段/昵称；401 会话失效；403 缺少能力或层级不允许；404 目标不可见；409 `auth_version_conflict`；413 请求体过大；503 数据库或投影不可用

路径 GUID 是唯一目标标识，body 不允许携带第二个目标。前端不得通过错误消息字符串判断权限或冲突。

## 3. 后端行为

新 v2 handler 使用现有 request ID、`no-store` 和用户认证中间件。它先完成严格解码，再调用专用的昵称更新服务；不调用旧的多字段 `UpdateManagedUser`。

服务在同一 MySQL 事务中按顺序锁定操作者和目标：

1. 重新读取操作者，要求 active、未删除、认证版本有效，并通过新鲜能力评估取得 `users.edit`。
2. 锁定路径 GUID 对应的未删除目标。
3. 应用既有层级规则：Admin 只能管理普通用户；Root 可以管理普通用户或 Admin；禁止自己、同级、上级和 Root 目标。
4. 比较 `expected_auth_version` 与锁定后的目标 `auth_version`；不一致返回 409，事务内无写入。
5. 规范化昵称；`null` 写入 SQL NULL。若规范化结果与当前值相同，返回当前投影，不写用户行或审计。
6. 有变化时只更新 `nickname` 与四个审计字段，并插入一个允许清单化的管理审计事件；用户更新和审计同事务提交或回滚。

昵称不是安全属性。成功修改不递增 `auth_version`，不撤销会话，不修改角色、状态、权限、套餐、分组、额度、凭据或 Redis。`expected_auth_version` 只防止操作者基于过期的安全状态执行资料编辑；它不是昵称字段的独立乐观锁。

成功响应通过已有安全投影生成，不返回内部 ID、密码、凭据摘要、票据或审计内部字段。数据库写入或审计失败返回固定 503，不能出现用户已改但响应成功、审计缺失或部分更新。

## 4. 前端行为

用户详情页在同时满足以下条件时展示“编辑显示名”：

- 当前身份拥有 `users.edit`
- 目标未删除且角色低于操作者
- 目标不是当前用户，也不是 Root
- 详情中存在合法的正整数 `auth_version`

编辑对话框只包含显示名字段。清空输入提交 `nickname: null`；非空值在客户端执行与服务端一致的首尾空白和 64 code point 检查，但服务端仍是最终权威。

提交体从当前对话框所有权快照生成，固定为 `nickname` 与 `expected_auth_version`。保存期间合并重复点击。成功后只在当前路由仍指向同一 GUID 时替换详情与对应列表行，并恢复焦点。409 时清除待提交状态、重新读取目标；不自动重放 PATCH，不覆盖新版本。401 走现有完整认证失效流程，403/404 清除编辑能力并刷新目标，503 保留安全失败提示供用户显式重试。

任何迟到响应不得跨越路由切换、身份 epoch、权限版本或对话框重新打开状态修改新页面。

## 5. 安全与兼容性

- 新界面只调用 v2 PATCH，不调用旧 PUT。
- 未知字段和重复字段必须在 handler 调用 service 前失败，防止借通用绑定器注入敏感字段。
- 能力与层级在事务内重新验证，不能只信任 JWT 或前端按钮可见性。
- 审计内容只记录操作者、目标、动作及“显示名已修改/清除”的结构化事实，不保存旧/新显示名文本，避免将用户资料复制到审计。
- 不新增迁移；复用现有 nullable `users.nickname` 与管理审计表。
- 不改变旧 PUT 的兼容行为，但新合同和前端明确不依赖它。

## 6. 验证与状态更新

后端验证覆盖：严格 JSON 正反例、伪造字段矩阵、能力与层级矩阵、目标不可见、版本冲突、空值清除、Unicode/64 边界、同值 no-op、并发安全状态变化、用户写入/审计/commit 故障回滚、精确响应 DTO/头以及旧 PUT 不被新界面调用。

前端验证覆盖：按钮可见性、精确请求体、客户端边界、重复提交、成功对列表/详情的同目标更新、409 刷新且不重放、401/403/404/503、路由/身份/对话框所有权竞态、焦点与键盘交互。最终执行前端全量测试与生产构建，并用可见浏览器完成 Root→User、Root→Admin、Admin→User、无权限和冲突路径的联合验收。

只有前后端合同一致、真实隔离 MySQL/Redis 验证、前端测试/构建、浏览器联合验收、独立质量与安全复审全部通过后，才把 A05 从 `BLOCKED_NOT_IMPLEMENTED` 更新为 `PASS_LIMITED_SCOPE`。其余 A06–A11、P01、P03–P08、R02 状态不得随本切片改变。本切片不授权生产迁移、部署或生产数据操作。
