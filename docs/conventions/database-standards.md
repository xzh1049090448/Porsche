# 数据库建模与持久化约束

本规范适用于 Porsche 中**所有新建数据库表、为已有表新增的持久化字段，以及相关的 Go 实体、迁移、Service 与测试**。它是强制性约束：需求、设计或历史代码与本规范冲突时，开发 Agent 必须先说明冲突并取得明确批准，不能自行绕过。

> 现有表不因本规范自动执行 `ALTER TABLE`。涉及既有 Python 共享 MySQL 表的统一改造，必须单独设计可回滚迁移并获得批准；不得依赖 GORM `AutoMigrate` 隐式修改生产共享表。

## 1. 主键与业务标识

每张业务表必须同时具备下列两个标识：

| 字段 | 数据库类型 | 用途 | 规则 |
| --- | --- | --- | --- |
| `id` | 现有主键类型 | 仅作数据库内部主键 | 仅用于主键、外键和内部关联；不得作为对外业务 ID、URL ID 或客户端可编辑标识。 |
| `guid` | `BIGINT` | 对外/业务唯一标识 | `NOT NULL`、唯一索引；使用雪花算法生成的**有符号 64 位整数**，在 Go 中映射为 `int64`。 |

- `guid` 不是 UUID 字符串，也不是自增列；禁止由客户端传入、修改或根据时间手工拼接。
- 雪花 ID 生成器必须是项目共用实现，保证并发安全、单实例单调递增，并在多实例部署时使用稳定且唯一的 worker/datacenter 标识。禁止各业务模块重复实现。
- 新模型推荐使用：`Guid int64 \`gorm:"type:bigint;not null;uniqueIndex" json:"guid"\``。MySQL 使用有符号 `BIGINT`，避免无符号值无法安全映射到 Go `int64`。
- 对外 DTO 默认使用 `guid`；如受兼容性影响必须继续暴露 `id`，必须在接口文档中注明例外和迁移计划。

## 2. 审计字段

每张业务表必须有以下四个字段：

| 字段 | 数据库类型 | 含义 |
| --- | --- | --- |
| `created_at` | `BIGINT` | 创建时间（Unix 毫秒时间戳，UTC） |
| `created_by` | `BIGINT` | 创建该记录的用户主键 `users.id` |
| `updated_at` | `BIGINT` | 最近一次更新时间（Unix 毫秒时间戳，UTC） |
| `updated_by` | `BIGINT` | 最近更新该记录的用户主键 `users.id` |

- 所有持久化时间字段一律使用 `BIGINT` 保存 **Unix 毫秒时间戳**；**禁止使用 `TIMESTAMP`、`DATETIME`、`CURRENT_TIMESTAMP` 或数据库时区隐式转换**。
- Go 实体使用 `int64` 保存时间戳。仅在 Handler/DTO 边界按 API 契约转换为 `time.Time` 或 RFC 3339 文本；写入值必须来自 UTC 的 Unix 毫秒。
- 无法归属具体用户的系统任务、数据导入或初始化数据可令 `created_by` / `updated_by` 为 `NULL`，并在业务审计事件中标记系统来源；禁止伪造用户名或以 `0` 代替用户 ID。
- 创建后 `created_at`、`created_by` 不得更新；更新操作必须同时写入 `updated_at`、`updated_by`，并由当前已认证用户或明确的系统执行者提供。

## 3. 用户与关联

- `users.id` 是注册用户表唯一、稳定的内部关联主键。
- 所有需要关联用户的表均使用 `user_id BIGINT`（或上述审计字段）关联 `users.id`；**禁止使用用户名、昵称、手机号、邮箱或任何可变展示字段作为关联键**。
- `user_id` 必须建立索引；业务需要时建立数据库外键，但外键类型、符号位与 `users.id` 必须完全一致。
- `users.guid` 用于用户的业务/对外标识，不改变任何表使用 `user_id -> users.id` 的关联规则。

## 4. 枚举持久化

- 所有业务枚举在数据库中必须保存为 `INT`，禁止存储枚举名称、字符串状态或数据库原生 `ENUM`。
- Go 代码为每个枚举定义显式、稳定的整数值及双向映射；禁止仅依赖可重排的 `iota` 顺序。
- 新增枚举值只能追加新整数值，已发布值的整数含义不得变更或复用。API 可按契约返回可读名称，但数据库仍只保存整数。
- 迁移历史字符串枚举时，必须提供可验证的映射、回滚方案及兼容读取期，不得隐式转换生产数据。

## 5. 业务逻辑删除

- 每张持久化数据库表必须有 `is_deleted INT NOT NULL DEFAULT 0` 字段，并建立适合常用查询的索引；`0` 表示未删除，`1` 表示已删除。
- 业务删除一律更新 `is_deleted = 1`，并同时写入 `updated_at`、`updated_by`；除经书面批准的数据生命周期清理任务外，禁止在业务代码中对持久化表执行物理 `DELETE`。
- 所有常规读取、列表、统计、授权校验和关联查询必须默认附带 `is_deleted = 0`。确需查询已删除记录的管理/恢复流程，必须显式声明该条件、验证权限并记录审计日志。
- 需要“软删除后可重用”的业务唯一字段，其唯一索引必须将 `is_deleted` 纳入组合索引，或采用等效的可验证设计；不得因逻辑删除导致后续新建记录永久触发唯一键冲突。
- 逻辑删除不是安全边界：涉及用户、令牌、权限或计费的删除操作必须先完成授权校验；被逻辑删除的用户/资源不得继续被认证、授权或计费路径使用。

## 6. Go / GORM 实现要求

1. 新持久化实体必须显式声明 `guid`、四个审计字段、字段类型、索引和必要的非空约束；审计时间使用 `int64` 的 Unix 毫秒字段，且不得只依赖 GORM 默认 `CreatedAt` / `UpdatedAt` 时间列。
2. 创建路径必须从共用雪花 ID 服务取得 `guid`，并在事务内写入创建/更新审计字段。
3. 更新路径必须保持 `guid`、`created_at`、`created_by` 不变，并原子写入 `updated_at`、`updated_by`。
4. Repository/Service 的用户关联查询只接收和比较 `users.id` / `user_id`；不得用用户展示字段查询授权归属。
5. 枚举入库和出库必须经过代码映射；不得将 `String()` 或用户输入直接持久化为状态值。
6. 业务删除必须通过 Service/Repository 的逻辑删除方法完成；普通查询应集中复用默认 `is_deleted = 0` 过滤，禁止遗漏。
7. MySQL 迁移必须使用显式、可审查的迁移文件。对 Python 共享库的表，必须遵守现有的“禁止隐式迁移旧表”保护。

## 7. 开发与评审门禁

所有涉及数据库模型、迁移、DAO/Repository 或写路径的 Agent 必须在开发前阅读本文件，并在交付前逐项确认：

- [ ] 新表有仅作主键的 `id` 和唯一、雪花生成的 `guid BIGINT`。
- [ ] 有 `created_at`、`created_by`、`updated_at`、`updated_by`；时间列是保存 Unix 毫秒的 `BIGINT`，不是 `TIMESTAMP` 或 `DATETIME`。
- [ ] 用户关联仅使用 `users.id` / `user_id`，不依赖用户名等展示属性。
- [ ] 枚举列是 `INT`，代码存在稳定的整数映射。
- [ ] 有 `is_deleted INT NOT NULL DEFAULT 0`；普通读路径默认排除已删除记录，删除路径不执行物理删除。
- [ ] 软删除后可重用的唯一字段已验证其组合唯一索引策略；授权、统计与关联查询已覆盖逻辑删除场景。
- [ ] 创建、更新、并发和权限相关测试覆盖 `guid`、审计字段、枚举映射与用户关联。
- [ ] 迁移已评审，不会隐式修改或删除共享 MySQL 的既有数据。

违反任一项时，安全审查或测试 Agent 必须阻止交付，除非仓库维护者书面批准了带迁移计划的例外。
